# Kiana 注释与文档写作规范

本文件是仓库级注释改造的**唯一写作标准**。所有参与本任务的实现者、审阅者与后续维护者
都必须遵守。它同时回答两个问题：**写什么**（覆盖定义）与**怎么写**（结构与语气）。

---

## 1. 目的

让一个**完全不了解本项目、Rust 基础一般**的读者，只依赖仓库内的文档与注释，就能：

1. 说清每个 crate 解决什么问题、为什么存在、与谁交互；
2. 沿着调用链读懂一次完整任务的执行过程；
3. 理解核心数据结构的不变量、状态机的转换、并发模型与错误传播；
4. 知道修改某处会影响哪些地方、有哪些边界条件与失败场景。

注释不是数量竞赛。**准确解释意图、机制、约束与设计原因**优先于覆盖行数。
无法从源码、测试或设计资料确认的内容，一律写入“待核实”，不得写成事实。

### 1.1 每个重要模块的验收清单

读完一个模块的文件级文档与关键注释后，新人应能回答下面 8 个问题；缺哪一项，就在
该模块的 `//!` 或核心项 `///` 中补哪一项（不要用逐行注释凑数）：

1. 它解决什么问题？
2. 为什么需要它——没有它会退化/失败成什么样？
3. 输入是什么，输出是什么（类型、单位、所有权/借用）？
4. 与哪些模块、调用方、被调用方交互？
5. 内部执行顺序是什么（阶段划分、状态转换）？
6. 为什么采用当前实现，而不是更直观的做法（约束、TS 对齐、性能/线程模型）？
7. 边界与失败模式是什么（错误类型、取消、超时、空值、并发竞争）？
8. 修改它会影响哪些地方（下游 crate、持久化格式、冻结契约）？

## 2. 硬性约束

1. **只允许修改注释和 Markdown。** 不得改动任何运行逻辑、API、函数签名、依赖、配置或测试行为。
2. **不得重构、重命名、重排或格式化代码。** 不得运行 `cargo fmt` 修改文件；只允许运行
   `cargo fmt --check` 做校验。
3. **不得删除或覆盖仓库中已有的用户改动。** 本仓库目前没有基线提交，改动前的文件内容以
   任务开始时的磁盘状态为准。
4. **新增注释必须是“插入”，不是“重写”。** 除非原注释与源码矛盾（需在报告中说明），
   否则保留原有精确的 TS 对应关系、字节级保真说明等内容，在其上补充教学式解释。
5. **示例代码默认不可执行。** 除已实际验证过的示例外，一律使用带 `text` 标记的代码块
   （```` ```text ````），避免 `cargo test --doc` 编译失败。不得引入未经验证的 doctest。
6. **Rustdoc 链接必须有效。** 公开文档中的 `[`符号`]` 只能指向同 crate 可见的项；
   私有项、跨 crate 未重导出的项一律用行内代码。`cargo doc` 不得新增警告。
7. **不得猜测。** 设计动机只能来自源码结构、测试断言、`spec/*.md`、`ARCHITECTURE.md`
   或本仓库文档。推测必须标注“推测”并列入待核实清单。

## 3. 覆盖定义

覆盖分为五层。统计时以**文件/符号清单**为准，不使用模糊百分比。

| 层级 | 对象 | 要求 | 可度量方式 |
|---|---|---|---|
| T0 | crate 根（`lib.rs` / `main.rs`） | `//!` 必须回答：职责、为什么存在、上下游、入口、核心类型、执行流程、失败模式、阅读顺序 | 28/28 crate |
| T1 | 每个非平凡源文件 | `//!` 模块说明：这个文件为什么存在、解决什么、被谁调用、主要流程；生成物须注明生成方式与修改禁忌 | 798 个源文件 |
| T2 | 公开 API 项 | `///`：语义、字段/参数、返回值、错误、不变量；已有文档只补缺失部分 | 11,935 个公开项 |
| T3 | 复杂函数/算法 | `//` 解释阶段、为什么这样实现、关键假设、复杂度（可确认时）、边界 | 由审阅者按清单抽查 |
| T4 | 特殊机制 | 状态机、并发/锁/取消、unsafe/FFI、持久化、外部 IO、错误恢复：单独成节说明 | 审阅清单逐项确认 |

**“非平凡”**：包含控制流、领域逻辑、跨模块协作或非显然约束的文件。纯类型再导出、
纯常量表、生成数据文件只需 T1 的文件级说明。

测试文件不逐文件加长注释；每个 crate 的测试策略、fixture 来源与“锁定什么行为”
汇总到 `docs/COMMENT_PROGRESS.md` 与 `docs/DEBUGGING_GUIDE.md`。

## 4. 由浅入深的写作结构

按对象复杂度选用栏目，不要求每项都写满：

1. **一句话**：它是什么。
2. **通俗解释**：用新手能懂的方式讲核心机制（可用类比，但类比后必须给出准确表述）。
3. **技术细节**：真实的数据结构、调用顺序、协议、边界。
4. **设计原因**：为什么这样实现；不这样会怎样；何时不适用。
5. **注意事项**：不变量、并发约束、失败模式、误用风险、相关模块。

函数注释至少说明：做什么、输入、输出、副作用、错误、关键边界。简单 getter、
显而易见的赋值、一行转发不写废话注释。

### 4.1 crate 根模板

```text
//! <一句话职责>
//!
//! # 这个 crate 解决什么问题
//! ...
//!
//! # 在系统中的位置
//! 上游：... 下游：... 对应 TS：...
//!
//! # 核心概念与类型
//! ...
//!
//! # 一次典型调用
//! 1. ... 2. ...
//!
//! # 边界与失败模式
//! ...
//!
//! # 阅读顺序
//! ...
```

### 4.2 模块文件模板

```text
//! <一句话>
//!
//! 为什么需要这个模块 / 它负责的边界；
//! 与哪些模块交互（调用方、被调用方）；
//! 主要流程或数据结构；
//! 重要约束（线程、顺序、IO、错误）。
```

**模块文档只写在源文件的 `//!` 里，不要给父模块的 `mod` 声明新增外层 `///`。**
这是 rustdoc 的一个作用域陷阱：当一个模块同时有“父模块里的外层 `///`”和“文件内的
`//!`”时，rustdoc 会把两段文档合并后放到**父模块作用域**解析链接。于是 `//!` 中原本
可以解析的短链接（`[`StoreFixture`]`、`[`ErasedValue`] 等指向本模块条目的名字）会全部
变成 `broken-intra-doc-links`。若目标文件历史上已有外层 `///`（如 `kiana-ai/src/lib.rs`），
其 `//!` 链接必须写成全限定形式 `[`crate::模块::条目`]`；新增文档不要制造这种局面。

### 4.3 状态机

必须列出：状态集合、每个状态的含义、允许的转换、触发条件、失败/取消时的行为、
不变量。用表格或编号列表均可，但要与代码中的分支一一对应。

### 4.4 并发

必须说明：保护对象、锁/通道类型、持锁范围、谁负责取消、任务生命周期、
顺序保证、潜在死锁或饥饿风险。**只写代码确实提供的保证**，不写“应该安全”。

### 4.5 unsafe / FFI

必须写明：所依赖的安全前提、调用者必须维护的不变量、越界/空指针/别名/线程归属
等具体风险。没有证据的安全论证不得编造；无法确认时标注待核实。

### 4.6 错误处理

说明错误来源、类型（`Result`/`Option`/错误事件/退出码）、传播路径、是否可重试、
调用方应如何恢复。不要只复述 `?`。

## 5. 语言与术语

- 正文使用准确、自然的简体中文；Rust 标识符、类型名、协议字段保持原文。
- 专业术语首次出现时解释，例如：“`crate`（Rust 的编译单元，一个库或二进制）”。
- 不写空话：“这里做了处理”“用于优化”之类无信息量的句子禁止出现。
- 不夸大：没有基准数据不写“性能更好”；没有证明不写“线程安全”。
- 尽量把“为什么”放在“是什么”之前或紧随其后。

---

## 6. 文件类型策略

| 类型 | 策略 |
|---|---|
| 生成/数据文件（如 `text_tables.rs`、模型目录数据） | 文件头说明生成来源、结构、为何不能手改；不逐项注释 |
| 协议/线格式文件 | 说明帧/字段、方向、版本兼容、错误码；与 `spec/*.md` 关联 |
| 平台层（unix/windows/wasm） | 说明平台差异、条件编译、不可用时的行为 |
| `bin/` 与 `main.rs` | 说明进程启动顺序、参数、退出码、运行时/线程模型 |
| 测试与 fixture | 不逐条注释断言；在模块头说明测试目标与 fixture 来源 |
| 大型纯函数/解析器 | 按阶段注释，给出输入输出示例与失败条件 |

## 7. 验证流程

每个批次完成后必须执行：

1. **差异纯度检查**：`tools/check_comment_only_diff.py` 对比基线快照，
   确认仅新增/修改注释行与 Markdown；任何代码行变化立即停止并报告。工具比较的是
   **过滤掉注释与空行后的代码行序列**（避免重复行造成的 diff 假阳性），因此代码行的
   增删或重排都会被检出。
2. **格式检查**：`cargo fmt --all -- --check`（不自动格式化）。注意 rustfmt 的一些启发式会受
   注释影响：例如给枚举变体补 `///` 后，rustfmt 可能把原本多行的结构体变体折叠成一行。
   一旦发现这种 diff，应删除/调整触发它的注释来恢复基线排版，**不得**重排代码。
3. **编译检查**：受影响 crate 的 `cargo check -p <crate> --all-targets`。
4. **文档检查**：`RUSTDOCFLAGS='-D warnings' cargo doc -p <crate> --no-deps`，不得新增警告；
   检查 intra-doc link 与代码块标记。注意 `rustdoc::private_intra_doc_links`：公开文档里
   链接 `pub(crate)`/私有项（如 `spawn_error_message`、`MAX_SAFE_INTEGER`）也会告警，
   这类目标应写成行内代码而不是链接。
5. **准确性抽查**：由独立审阅者对照源码、调用方、测试逐条核对，重点排查
   凭空推断的动机、并发保证、性能结论。
6. **覆盖率统计**：重新运行 `tools/doc_inventory.py`，更新
   `docs/COMMENT_PROGRESS.md` 的实测数字。

运行成本过大时，先执行受影响 crate 的检查，并在进度文件中记录未执行项与原因。

## 8. 反模式（禁止）

- 逐行翻译代码（`// 给 x 加 1`）。
- 对显然的 getter/setter、简单 `return`、纯转发函数写长注释。
- 用“优化性能”“线程安全”“等价于 TS”作为没有依据的结论。
- 把 `spec/*.md` 的大段内容复制进源码；应给出精确引用与最小必要解释。
- 修改代码“顺手修复”注释时发现的问题；发现问题只记录，不越权修改。
- 为凑覆盖率给生成数据逐项加注释。
