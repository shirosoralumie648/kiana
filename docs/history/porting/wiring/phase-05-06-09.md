# Wire C — 第 5/6/9 周共享接线与本波集成验证

日期：2026-11-07
范围：`docs/history/porting/handoffs/phase-05.md`、`phase-06-compaction-output.md`、`phase-09-request-policy-otel.md` 的跨 crate
接线与集成验证；验收标准见 `docs/history/porting/plan.md` 第 5/6/9 周。

本文件记录实际应用的 handoff、与 handoff 的核对结论与有意偏差、共享文件改动、
真实检查/测试输出、剩余缺口，以及给后续波的风险。

---

## 1. 应用的 handoff 与顺序

按依赖顺序应用：

1. **week 5（MCP + Skills）**：MCP annotations → 权限、`AllowAlways` 持久授权限制、
   `skill` 工具注册/激活/撤销、系统提示技能索引（模型窗口 1% 预算 + `paths` 可见性）。
2. **week 6（压缩与工具输出）**：会话级 ArtifactStore、工具输出预算包装、压缩门控、
   prune → prepare → 结构化摘要、all-or-nothing 提交、压缩后 read gate/恢复附件、
   聚合 tool-result 预算。
3. **week 9（Provider 策略 + OTel）**：请求前输入预检（零请求失败 + 先压缩一次）、
   错误分类对重试的否决、usage 记账进入遥测、SessionTelemetry/AgentRunCollector
   接入会话生命周期、退出前 flush。

工具执行顺序保持 `hook 改写 → 扩展改写 → 记录触达路径 → 权限判断 → 执行`；
权限内部顺序为 `engine.evaluate（含 deny）→ 技能激活只把 Ask 放行 →
MCP annotations（只对 Mcp 动作，且 explicit deny 优先）`。任何一层都不会把
deny 改成 allow。

## 2. Week 5：MCP annotations 与 Skills

### 2.1 已接线

- `Core::permission_refusal_inner`：
  - 有 `skill` 工具时用 `evaluate_with_activations(engine, skill_tool.activations(),
    request, now)`；每轮先 `prune_expired`。`Deny` 原样返回，只有 `Ask` 会被激活的
    `Allow` 规则放行。
  - `ActionKind::Mcp` 再应用 `apply_mcp_annotations`；`explicit_deny` 通过遍历
    `engine.policy().rules` 中命中的 `Deny` 规则计算，保证 `readOnlyHint` 不会给显式
    deny 翻案。
- `Core::persist_approval`：`allows_persistent_approval(annotations)` 为假时拒绝
  `AllowAlways`（destructive/open-world MCP 工具只能逐次批准，规则列表不增长）。
- `Core::tool_annotations`：从 `tool_definitions` 读 `definition.annotations`，
  读取前 `flush_pending_tool_refresh`（annotations 可随 `tools/list_changed` 变化，
  不做缓存）。
- `skill` 工具：
  - `ensure_skill_tool` 懒构造 `Arc<SkillTool>`；`refresh_tool_registry` 在
    `all_custom_tools` 中注册 `create_skill_tool_definition`（Direct 曝光、默认激活）。
  - 技能定义来自 loader 的 `Skill` 快照（`skill_definitions_from_skills` 复用
    `load_skill_definition_from_file` 读取正文/frontmatter）；`build_runtime`
    强制刷新，普通系统提示重建按“名字+路径”缓存，避免每轮读盘。
  - `AgentSession::dispose` 调用 `SkillTool::end_session()`；`deactivate` 已由
    `SkillTool` 自身提供。
- 系统提示：
  - `rebuild_system_prompt` / `prepare_prompt_and_tool_loadout` 用
    `format_skill_definitions_for_prompt(definitions, reader,
    skill_index_budget_chars(模型窗口), touched)` 生成 `sections["skills"]`，
    同时把默认 `skills` 列表置空，避免重复生成。
  - `paths` 可见性依赖 `Core::touched_paths`：`before_tool_call` 在 hook/扩展改写后
    用 `PermissionRequest::from_tool_call_with` 提取 `paths`/`read_paths` 并记录；
    直接执行路径 `tool_permission_refusal` 也记录。
  - 技能索引每轮在 `prepare_prompt_and_tool_loadout` 重新计算，因此第一次 read
    `src/lib.rs` 后下一轮系统提示增量会出现 `paths=["src/**/*.rs"]` 的技能。

### 2.2 与 handoff 的偏差（有意）

1. **只有在存在技能定义时才注册 `skill` 工具。** handoff 建议无条件注册并默认激活；
   实测无条件注册会给所有无技能会话的 tools schema/系统提示增加约 100+ token，
   改变既有压缩回归测试的上下文预算。无技能时注册一个永远无法成功调用的工具没有
   收益，因此按“定义非空”注册。
2. **技能定义从 loader 的 `Skill` 快照派生**，而不是再用
   `load_skill_definitions(LoadSkillsOptions { skill_paths, ... })`。会话层拿不到
   loader 内部的 `additional_skill_paths`/`no_skills`；复用 loader 已完成发现/冲突处理
   的 `Skill` 列表可保证与系统提示里的技能集合一致。
3. **`context: fork` 未实现**：`SkillActivation.context` 只携带值，子会话创建/结果
   回传仍缺 API。
4. **激活的 `hooks` / `agent_scope` / `model` / `effort` 运行时应用未接线**：
   这些字段随 `SkillActivation` 返回，但会话不会临时合并 hook/限制子代理/覆盖模型。
5. **`/mcp` 结构化状态未进入 manager 详情页**：`McpServerStatus` 已可用，本波只保证
   文本状态行（week 5 lane 已完成）。

## 3. Week 6：压缩生命周期与工具输出

### 3.1 已接线

- **ArtifactStore**：`Core::artifact_store()` 惰性创建（session dir 为空时返回
  `None`）；同一会话复用同一个 `Arc`。
- **工具输出预算**：`refresh_tool_registry` 在 `wrap_registered_tools` 之后对
  builtin/extension 工具套 `wrap_agent_tool_with_output_budget`；无 store 时保持原样。
- **压缩门控**：`Core::compaction_gate`（`Mutex<CompactionGate>`）。自动压缩开头
  `check(history_hash, now)`；`NoOpCached`/`Cooldown`/`Disabled` 直接返回 `false`。
  成功记录 `Succeeded`，无可压缩内容记录 `NoOp`，摘要失败记录 `Failed`。
  手动压缩不检查 no-op 缓存（用户显式要求），但成功/失败仍更新门控状态。
- **prune + prepare**：`run_auto_compaction` / `Core::compact` 都改用
  `prepare_with_pruning(&path_entries, &settings, &PruneConfig::default())`；
  `pruned.entries` 只用于本次摘要，摘要成功前不写回。
- **结构化摘要**：`run_default_compaction` 改用 `compact_with_structured_template`
  + `CompactModelOptions`；保留 split-turn 拼接、文件清单与重试回调。
- **all-or-nothing 提交**：
  1. 摘要前捕获 `kiana_session_core::compaction_support::HistorySnapshot`；
  2. 摘要成功后校验历史未变；
  3. `CommitTransaction` 先写 prune 的 `append_context_edit`（`PruneRecord.notice`），
     重新捕获快照，再 `append_compaction_transactional`；
  4. 任一步失败回滚内存并返回错误。自动/手动两条路径一致。
- **压缩后恢复**：
  - 压缩前 `read_state.snapshots(5)`；成功后 `read_state.clear()` +
    `restore_snapshot`（指纹不一致/缺失只跳过）。
  - `build_recovery_attachment`（文件/技能/plan/工具增量）写入
    `pending_recovery_attachment`，在下一次 `prepare_request` 作为 **system 消息**
    注入请求副本；不持久化、不伪造 tool result。
  - 附件若会让请求超出模型窗口则丢弃（恢复是增强，不应制造 overflow）。
- **聚合 tool-result 预算**：每次 `prepare_request` 开头调用
  `enforce_aggregate_tool_result_budget(branch, 50_000, store, config)`；
  `cleared` 条目用 `append_context_edit` 持久化，占位符带 artifact 路径。

### 3.2 与 handoff 的偏差（有意）

1. **确定性 fallback 只用于手动压缩。** handoff §3.2 建议默认路径失败时都尝试
   `build_fallback_result`。但既有回归测试锁定自动压缩的旧语义：
   - `notifies_extensions_when_auto_compaction_fails` 要求 threshold 摘要失败时发出
     `session_compact_failed`，不提交、不重试；
   - `keeps_omissions_and_does_not_retry_when_recovery_compaction_fails` 要求 overflow
     摘要失败时保留 omissions、不重试。
   为不改变这些已冻结的自动恢复语义，自动路径失败仍返回原错误；手动 `compact()`
   （用户显式请求）在摘要失败时使用确定性 fallback，并把 `usage=None` 的结构化摘要
   提交。fallback 仍满足“严格更小”约束。
2. **PTL `plan_ptl_retries` 未接入**：保留现有
   `overflow_recovery_attempted`（一次 compact+retry、第二次明确报错）状态机。
   `plan_ptl_retries` 是纯函数，没有在会话请求副本上应用。
3. **恢复附件预算**：没有把 `RecoveryAttachment.warnings` 变成用户可见事件
   （`AgentSessionEvent` 没有通用 Notice 变体）；只保留在附件文本/内部。
4. **plan 恢复**：`RecoveryInput.plan` 恒为 `Default`（会话层没有 plan mode 状态
   读取入口）；active plan 路径也没有传给 `PruneConfig::with_plan_paths`。
5. **磁盘半行回滚**：`CommitTransaction` 只保证内存状态一致（模块文档已声明）；
   写盘中途 IO 错误/崩溃仍可能留下残行。

## 4. Week 9：Provider 策略、usage 与 Telemetry

### 4.1 已接线

- **SessionTelemetry 构造**：`Core::new` 用 `OtlpExporter::from_env()`；没有 endpoint
  时为内存模式；`with_exporter` 注入。新增 `kiana-session` → `kiana-telemetry` 依赖。
- **事件埋点**（`observe_run_telemetry`，在 `handle_agent_event` 归一化后调用）：
  - `AgentStart`：每个 run 新建 `AgentRunCollector`，记录可用工具名，开始
    `invoke_agent` 根 span；
  - `TurnStart`/`TurnEnd`：`kiana.session.turn` span（duration/stop reason），
    `TurnTracker` 预留给 TTFT/TTFM（流式 token 尚未接入）；
  - `MessageEnd`（assistant）：`record_api_call`（provider/model/usage/duration/
    stop reason/error）；成功路径用 `account_provider_usage` 计算 canonical usage 与
    `cost_source`（价格未知时回退 provider 上报，并记录来源）；
  - `ToolExecutionEnd`：`record_tool_call`（名称/ID/status/duration）；
  - `AgentEnd`：结束根 span（collector 自行 `mark_run_ended`）；
  - 压缩成功：`record_compaction`（trigger/input/output tokens/outcome/duration）。
- **AgentRunCollector**：`AgentSession::run_summary()` / `run_coverage()` 暴露最近
  run 的汇总与覆盖；`observe_event` 与直接 API 不混用。
- **flush**：`AgentSession::flush_telemetry()`；`AgentSessionRuntime::dispose` 与
  会话替换路径在 `session.dispose()` 前 await flush（exporter 不可达不影响退出）。
- **输入预检**：`prepare_request` 在非虚拟/虚拟路由后调用
  `ensure_request_fits_context`：估算放不进窗口且存在可压缩内容时先
  `run_auto_compaction(Overflow)`，仍放不进则写 `pending_stream_error`，由标准流函数
  入口在下一次 stream 调用失败，**零 provider 请求**；压缩设置关闭或没有可压缩内容时
  保留旧行为（交给响应后 overflow 判定）。
- **错误分类**：`is_retryable_error` 先用
  `classify_provider_error_with_typed` 做不可重试否决（Auth/Quota/ContextWindow/
  InvalidRequest），Unknown 时回退既有正则判定，避免扩大重试面。
- **sandbox trace 编译修复**：`crates/kiana-evals/src/native.rs` 的 `SpawnOptions`
  字面量补 `..SpawnOptions::default()`（week 9 lane 新增 traceparent/tracestate
  字段后的共享编译修复）。

### 4.2 未接线 / 偏差

1. **provider 能力门、输出预算 `max_tokens`、cache 断点没有接线。** 这些必须在最终
   provider payload（`kiana-ai` 适配器）上生效，本波共享文件所有权不包含
   `crates/kiana-ai/src/**` 或 `kiana-agent-core/src/agent_loop.rs`；会话层无法写
   `max_tokens`/注入 `cache_control`。`prepare_request` 纯函数已由 week 9 lane
   单元/集成测试覆盖，接线点仍见 handoff 第一节。
2. **faux provider 跳过硬预检/恢复附件。** faux/mock 的 `context_window` 只用于驱动
   会话阈值测试，provider 不执行窗口限制；硬失败会改变脚本化轨迹与既有回归测试的
   call/usage 断言。真实 provider 仍执行零请求预检。
3. **`TRACEPARENT` 没有传入 bash 子进程。** `crates/kiana-tools/src/bash.rs` 不在本波
   共享文件白名单；`SpawnOptions.traceparent/tracestate` 已存在，接线仍需在 bash
   执行器填字段（或用 `with_traceparent`）。
4. **hook / startup phase 埋点未接入**：run/turn/API/tool/compaction 已覆盖；
   `record_hook_run` 需要在 hook 执行点计时，`record_startup_phase` 需要在
   `create_agent_session` 分阶段计时，均未接线。
5. **TTFT/TTFM 为空**：流式 `assistant_message_event` 没有逐 token 喂
   `TurnTracker`；当前 turn span 只有总 duration 与 stop reason。
6. **OTLP 离线行为**：exporter 不可达只影响 `flush` 结果；没有重试/背压。

## 7. 剩余缺口

1. **MCP annotations 的端到端测试**：策略函数与 `permission_refusal_inner` 已接线，
   但本波没有可用的进程内 MCP server fixture 覆盖“destructive → ask / read-only 放行 /
   显式 deny 优先 / AllowAlways 拒绝”的完整会话链路；`kiana-resources` 的单元测试
   覆盖纯策略。
2. **技能 `context: fork`、激活 hooks/agent_scope/model/effort**：未实现。
3. **技能 `paths` 的下一轮系统提示增量**：代码已按 touched paths 重建，但没有专门的
   回归用例；本轮只由既有系统提示测试间接覆盖。
4. **provider 能力门/输出预算/cache 断点**：见 §4.2；必须在 `kiana-ai` 适配器接线。
5. **PTL 头部丢弃**：仍使用 `overflow_recovery_attempted` 的一次 compact+retry。
6. **恢复附件只注入一次**：在 `prepare_request` 中取走；若同一请求被 agent loop 重试
   （非压缩失败），附件不会重复注入（这是有意的，避免 token 累积）。
7. **Telemetry**：TTFT/TTFM、hook/startup 埋点、gRPC e2e、内容捕获运行期切换仍缺
   （部分为 week 9 lane 已声明的 crate 级缺口）。
8. **TRACEPARENT → bash 子进程**：编译已修复，注入未接线。
9. **聚合预算的持久化**：每次请求前都扫描分支；虽然已清除条目会被占位符前缀跳过，
   扫描成本随历史增长（无增量索引）。

## 8. 给后续波的风险

- **`skill` 工具默认激活**：有技能定义的会话会多一个 Direct 工具与一条 prompt
  snippet，系统提示 token 增加；对上下文预算敏感的 provider/回归需要重新校准。
- **`paths` 技能索引每轮重算**：`format_skill_definitions_for_prompt` 是确定性的，
  但 touched 集合增长会让描述均分预算变化，系统提示可能在某轮出现增量（预期行为）。
- **自动压缩仍是失败即停**：确定性 fallback 只在手动压缩启用；如果后续产品要求
  “所有压缩都有结果”，需要同时修改 `notifies_extensions_when_auto_compaction_fails`
  与 overflow 回归的契约。
- **压缩门控的 5 分钟冷却**：自动压缩失败后会冷却，用户连续触发阈值压缩可能看到
  “没有压缩”而不是重复失败；诊断需要读 `CompactionGate`（目前没有公开访问器）。
- **aggregate budget 写 context_edit**：会在请求前改变会话条目（投影），扩大会话
  文件；占位符不含原内容（artifact 路径可回读），secret 已在落盘时 redaction。
- **恢复附件**：只在真实 provider 注入；faux/mock 跳过。后续接新测试 provider 时需要
  识别该 provider，否则会改变脚本轨迹。
- **预检的估算误差**：`estimate_context_tokens` 是字符启发式；对中文/代码可能偏差
  10%+，硬失败只在“确认可压缩但仍放不下”时发生，仍可能误杀本来能成功的请求。
- **遥测 in-memory**：无 exporter 时 `SessionTelemetry` 仍记录 span/task；大量事件下
  有内存增长风险，生产应配置 exporter 或考虑采样。
