# Wire B — 第 4/7/8 周共享接线与本波集成验证

日期：2026-11-07
范围：`docs/history/porting/handoffs/phase-04.md`、`docs/history/porting/handoffs/phase-07.md`、
`docs/history/porting/handoffs/phase-08.md` 的跨 crate 接线。

本文件记录实际应用的 handoff、核对结论与偏差、共享文件改动、真实检查/测试输出、
剩余缺口，以及给后续波的风险。

## 1. 应用的 handoff 与顺序

按依赖顺序应用：

1. **week 4（Hooks）**：PreToolUse → 扩展 `tool_call` → 权限 → 执行；
   PostToolUse / PostToolUseFailure、PermissionDenied、UserPromptSubmit、Stop、
   PreCompact / PostCompact、SessionStart / SessionEnd、审计与每回合状态。
2. **week 7（编辑体验）**：`tools.applyPatch.models` 的会话级模型路由、`edit` /
   `apply_patch` 的双向名字映射、模型切换时重建工具定义。
3. **week 8（loop guard / budget）**：`CreateAgentSessionOptions` 字段、模型解析后的
   `budget_handle` 构造、`AgentOptions` 透传。

与原计划的顺序一致：hook 改写先于权限判断，任何 deny 优先；apply_patch 路由只替换
`edit` 槽；loop guard / budget 通过 `Agent` 内部配置生效，不改变工具执行顺序。

### 1.1 Week 4 与 handoff 的核对结果

handoff 的公开 API 与实际 `kiana-hooks` 完全一致（`HookRegistry::add_source`、
`HookRunner::run_event_with_state`、`HookTurnState`、`HookOutcome` 等），按 handoff
的接线点应用，但有几处按实际代码调整：

- `PermissionRequest` 的参数字段是 `args`，不是 `tool_input`（handoff 的示例文字）。
- `PostToolUseFailure` 的错误文本来自 `context.result.content` 的文本块；直接
  `join("\n")`，不再经过 `content_text_user_content`（该函数要求 `&UserContent`）。
- `before_tool_call` 实际先跑扩展再跑权限；已改为 hook → 扩展 → 权限。
- `Core::compact` / `run_auto_compaction` 的 `session_before_compact` 扩展事件在
  `prepare_compaction` 之后；PreCompact hook 放在扩展事件之前，因此 hook deny 可以
  取消扩展压缩。
- SessionStart / SessionEnd 在 `kiana-session` 没有统一的初始上下文注入点 /
  同步生命周期；实现为 best-effort 审计（见缺口）。
- `allowManagedHooksOnly` 为真时整体停用 user/project/local hooks：`kiana-hooks`
  目前没有 `Managed` 来源，按 handoff §11 的最安全做法处理，并写入启动诊断。

### 1.2 Week 7 与 handoff 的核对结果

- `create_all_tool_definitions_for_model` 已在 `kiana-tools/src/index.rs` 就绪，
  会话层在 `Core::builtin_tool_definitions` 统一使用它。
- handoff 的“键仍是 `ToolName::Edit`、其它代码都按 `definition.name` 工作”只对
  工具注册表/系统提示成立；**激活名单与允许列表仍按名字查找**。如果只替换定义，
  默认激活名单里的 `edit` 会在 `apply_tool_loadout` 里查不到 `apply_patch`，导致
  编辑工具直接消失。本次新增双向映射：
  - `edit` → `apply_patch`（`canonical_tool_name`，用于激活名单/pending/loadout）；
  - `apply_patch` → `edit`（`allowlist_tool_name`，用于 `--tools`/`exclude` 配置）。
- `tool_definitions` 表的键改为 `definition.name`（否则 `tool_exposure` /
  `is_declarable` 按实际名字查不到）；builtin 的 source info 路径也使用
  `definition.name`。
- 模型切换（`set_model` / `cycle_model`）会重建内建工具定义，否则路由只在启动时
  生效。

### 1.3 Week 8 与 handoff 的核对结果

- `AgentOptions` 的 `loop_guard` / `budget` 字段存在，`Agent` 的
  `loop_guard()` / `budget()` / `set_*` 访问器存在。
- 按 handoff 在 `sdk.rs` 增加 `Option<LoopGuardHandle>` 与 `Option<BudgetConfig>`；
  预算在模型解析之后用 `budget_handle(config, &model)` 构造，没有模型时忽略。
- `Agent::execute_run` 会把 `LoopDetected` 合成为 assistant 失败消息，因此
  `session.prompt()` 可能同步返回 `Ok`；本次测试同时断言 `LoopGuard::stopped()`
  与 transcript 里的 assistant `errorMessage`，不依赖 `prompt` 的返回值。

### 2.1 与 handoff 的偏差（有意）

1. **week 7 的 `kiana-config` schema 字段未加**：Wire B 的共享文件所有权不包含
   `kiana-config`，因此没有在 `Settings`/`SettingsInput` 增加 `tools` 字段，也没有
   同步 `tests/config_schemas.rs` 的 59/57 计数。改为读取合并后 `Settings` 的
   `raw("tools")`，再交给 `ApplyPatchSettings::from_config`；线格式与 handoff 建议
   完全一致（`tools.applyPatch.models` / `tools.apply_patch.models`），未知键跨层按
   对象递归合并。影响：managed/system 层的 `tools` 不进入 `SettingsManager` 的合并
   （与 handoff 方案相同，后者也只读 `get_settings()`）；严格 schema 诊断会把
   `tools` 当作未知顶层键报告（不阻止加载）。
2. **SessionStart / SessionEnd 只执行与审计**：`additionalContext` 没有稳定的初始
   system 消息注入点；`system_messages` / `suppress_output` 也没有用户可见通道。
3. **hook 的 `Ask` 接现有审批 UI**：有 `ExtensionUiContext` 时复用
   `ask_for_approval`；没有 UI 时 fail-closed 转 block。批准只对本次调用生效，不写入
   持久规则，且批准后仍会经过权限层。
4. **`edit_tool_name` 的激活映射**是 handoff 没写到的必要修复，见 §1.2。

## 3. 执行顺序与 deny 优先（代码核对）

`Core::before_tool_call`（`crates/kiana-session/src/agent_session.rs`）：

1. `pre_tool_use_hook`：用当前 `context.args.get()` 跑 hook；
2. `outcome.blocking_error()` 存在 → 直接 block（`blocking_error()` 只消费一次）；
3. `Ask` → 审批 UI / 无 UI fail-closed；
4. `updated_input` → `context.args.set(updated)`（整体替换，不 merge）；
5. 扩展 `extension_before_tool_call`（仍可 block / 改写）；
6. `permission_before_tool_call`：权限层看到的是 hook + 扩展改写后的参数；
7. 权限 `Allow` 后才执行。

`PermissionDenied` hook 在 `refusal_for` 拿到拒绝原因之后运行：`retry: true` 只追加
“可以重试一次”的提示，feedback 追加为模型可见文本，绝不会把 deny 改成 allow 或自动
重放调用。

Stop 的 `Ask`（deny 上限触发后的降级）按“不继续”处理，避免 hook 借降级无限续命。
Stop deny 的 `blocking_error()` 作为 steering 消息注入一次并返回 `true`。

## 5. 剩余缺口（未接线，非本波退化）

1. **`tools` 的 typed settings 字段**：见 §2.1；后续若把 `kiana-config` 纳入共享
   范围，建议增加 `tools.applyPatch.models` 并同步 `SettingsInput`/校验器/59-57 计数，
   然后让 `Core::apply_patch_settings` 直接读 typed 字段。
2. **SessionStart `additionalContext`**：只审计；需要决定注入点（初始 system 消息 /
   `${hook-context}` 系统附件）。
3. **hook 的 `systemMessage` / `suppressOutput`**：没有用户可见事件通道；当前忽略。
4. **managed hooks**：`HookSource` 没有 `Managed` 变体，`allowManagedHooksOnly=true`
   时所有 hooks 被停用（安全但功能缺失）。
5. **hook audit 的可观察性**：记录保存在内存环形缓冲，只有
   `AgentSession::hook_audit_records()` 访问器；没有映射到 `AgentSessionEvent` 或
   落盘。进程退出即丢失。
6. **SessionEnd 的其它 teardown 路径**：只在 `AgentSessionRuntime::dispose()` 接线；
   switch/fork/import 的替换路径没有单独运行 SessionEnd。
7. **week 8 的 context report / observe_condensation**：可选接线，未做；`compact()`
   仍不产生 `CondensationEvent`。
8. **apply_patch 的 TUI 渲染与 SDK 导出**：week 7 的可选项，未做；`StreamingPatchParser`
   已就绪。
9. **async hook 的全局并发上限**：crate 缺口，会话层不会补。

## 6. 给后续波的风险

- **hooks 从“配置存在”变成“启动即执行”**：任何用户/项目 settings 里的 `hooks`
  现在会被 `Core::new` 加载。项目层仍受 trust gating，但 user 层无需 trust；发布前
  要做一次真实 settings 的冒烟。
- **同步 hook 在工具路径上**：PreToolUse / PostToolUse 的 command hook 默认 30s
  超时，会直接拖慢每次工具调用；Stop hook 还会拖慢回合结束。没有全局并发上限。
- **`HookRunner::new` 总是构建 reqwest 客户端**：即使没有任何 hook 配置，每个会话
  创建都会初始化 HTTP client。若启动性能敏感，可改为“注册表为空时不构建 runner”。
- **hook Ask 与权限 Ask 共用 UI**：审批文案来自 hook 的 `reason`；后续若 UI 需要
  区分来源，需要在 `ask_for_approval` 的 prompt 前加标记。
- **工具名映射是名字级的**：`ToolName::Edit` 的键仍是 `edit`，但任何新代码如果按
  `base_tool_definitions` 的键反查模型可见名字，必须改读 `definition.name`；激活
  名单两侧都要经过 `canonical_tool_name` / `allowlist_tool_name`。
- **`set_model` 现在会重建工具定义**：如果在 run 中调用，会走
  `pending_tool_refresh` 延迟刷新；不要在扩展派发内部直接调用。
- **Stop hook 每次 settle 都会运行**：如果 hook 慢或返回 deny，会明显改变回合
  节奏；deny 上限达到后 `Ask` 被当作“不继续”，这是刻意的防死循环语义。
- **`SessionStart` 在 `bind_extensions` 运行**：不调用 `bind_extensions` 的嵌入方
  （纯 SDK 无 UI）不会触发 SessionStart hooks；若产品要求 SDK 也触发，需要在
  `create_agent_session` 的异步路径里补一次。
- **预算 `cost_unknown`**：会话层没有 UI 呈现；调用方需要读
  `BudgetSnapshot.cost_unknown`。`TurnCapped` / `TimeCapped` 不产生 assistant
  消息，调用方不能只看 `prompt` 返回值。
